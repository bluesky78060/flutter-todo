## 먼저 밝힐 절차 이탈

**플랜 리뷰가 구현보다 먼저 이뤄지지 않았다.** 사용자 요청("위젯에서 완료
가능하도록 해줘")을 받고 조사 → 구현 → 문서화 순으로 진행했고, 이 문서는
구현 후에 작성됐다. 규칙상 순서는 Discovery → 플랜 → 플랜 리뷰 → 구현이다.

기록을 사실대로 남긴다. 이 문서는 "구현 전 승인"이 아니라 **"구현된 설계가
방향 문서와 맞는지에 대한 사후 점검"** 이다.

## 리스크 — 플랜이 짚었는가

### 짚은 것

1. **슬롯 인덱스 불일치** — 배열 위치와 저장 슬롯 번호가 다른 문제. 플랜의
   "핵심 판단 1". Android 가 `todo_index` 를 쓰는 이유(필터가 없어 우연히 맞음)
   까지 밝혔다.
2. **toggle vs set 어긋남** — 완료가 되돌아가는 사고. "핵심 판단 2".
3. **진행률 오염** — 미래 일정 완료 시 `3/2`. "핵심 판단 3".

### 플랜이 충분히 다루지 않은 것

**R-1. Flutter 쓰기와 익스텐션 쓰기의 경쟁 조건.**
익스텐션이 슬롯을 당기는 사이 앱이 `updateWidget()` 으로 같은 키를 덮어쓸 수
있다. 플랜은 "하지 않는 것"에도 넣지 않고 그냥 언급이 없다.

완화되어 있는 정도: 익스텐션 실행은 앱이 포그라운드가 아닐 때가 대부분이고,
앱이 다시 열리면 `checkAndRefreshWidget` 이 DB 기준으로 10칸을 통째로 다시
쓴다. 즉 **어긋나도 다음 재진입에 수렴한다.** 다만 그 사이 위젯이 잠깐 옛
항목을 보일 수 있다.

→ 적대적 검증 레인에 이 항목을 명시적으로 넘겼다.

**R-2. 자동 검증이 닿지 않는 범위가 기능의 핵심이다.**
"탭이 인텐트를 부르는가"는 실기기에서만 확인된다. 플랜은 이를 표에 적었지만,
**확인 전에는 완료로 보고하지 않는다**는 조건을 걸지 않았다.

→ 코드 리뷰 문서에서 미검증 항목으로 분리하고, 사용자 확인 요청을 남긴다.

## 판정

**조건부 통과.** R-1 은 적대적 검증 결과를 보고 판단한다. R-2 는 절차로 막는다.
