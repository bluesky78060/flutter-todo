# Discovery — DTA-3-4: 범위 일정(시작일~종료일) 지원

- 작성일: 2026-08-21
- 티켓: `DTA-3-4`
- 상태: **방향 확정** — 사용자와 7개 카테고리 문답 완료

## 배경

사용자가 *"범위가 있는 일정 등록이 안 되는 것 같다"* 고 신고했다.
조사 결과 세 가지가 겹쳐 있었고, 앞의 둘은 `DTA-3-1`에서 처리했다.

| # | 문제 | 처리 |
|---|---|---|
| 1 | 동기화 버튼이 스텁이라 아무것도 등록되지 않음 | DTA-3-1 완료 |
| 2 | 종일 이벤트 `end.date` 버그로 등록 거부 | DTA-3-1 완료 |
| 3 | **범위 일정 필드 자체가 없음** | **이 티켓** |

`Todo`의 날짜 필드는 `dueDate` 하나뿐이다. 앱 전체에 `showDateRangePicker` 사용처가 0건이다.

> **혼동 지점**: 반복 설정 다이얼로그의 "종료일"은 RRULE의 `UNTIL`이다.
> *반복을 언제까지 되풀이할지*의 경계이지 일정의 기간이 아니다.

## 1. 목표 (Why) — 무엇을 해결하는가

**여러 날에 걸친 "하나의 사건"을 표현한다.** 출장·여행·휴가가 대표 사례다.

사용자 확인: 기간 자체가 하나의 사건이며, **중간에 매일 뭔가 하는 작업형이 아니다.**
이 구분이 이후 설계를 전부 갈랐다 — 작업형이었다면 날짜별 진행 상태가 필요했을 것이다.

## 2. 사용자 (Who)

앱 소유자 본인. 다중 사용자 협업 시나리오는 없다.

## 3. 범위 (What) — 확정된 설계

### 3-1. 데이터 모델: `startDate`만 추가, `dueDate`를 종료일로 재해석

| 안 | 판단 |
|---|---|
| **채택** `startDate` 추가 + `dueDate` = 종료일 | `dueDate`의 기존 의미(마감일=종료일)가 유지된다. `startDate == null`이면 **지금과 완전히 동일하게** 하루짜리로 동작하므로 기존 데이터와 코드가 그대로 산다 |
| 기각 `startDate`/`endDate` 신설 | `dueDate`와 `endDate`가 공존해 어느 쪽이 진짜인지 혼란이 생기고, **255곳을 모두 검토**해야 한다 |

`grep -rn "dueDate" lib/ | wc -l` → **255** (25개 파일). 이 숫자가 판단의 근거다.

### 3-2. 완료 단위: 일정 통째로 하나

체크박스는 하나다. 날짜별 체크가 아니다.
기존 `Todo` 구조를 그대로 쓸 수 있어 별도 테이블·통계·위젯 파급이 없다.

### 3-3. 캘린더 표시: 기간의 모든 날짜에 표시

`table_calendar: ^3.1.2`를 쓰고 있다. `eventLoader`가 날짜별 콜백이므로
**기간에 걸친 날짜 전부에 마커를 찍는 것은 기본 기능으로 가능**하다. 추가 의존성이 없다.

가로 막대(구글 캘린더 스타일)는 `calendarBuilders` 커스텀이 필요해 기각했다.

현재 `calendar_screen.dart:121-136`의 `_getTodosForDay`는 `dueDate` **하루에만** 매칭한다.
이 함수가 기간을 이해하도록 고치는 것이 핵심 변경 지점이다.

### 3-4. 알림: 시작일에만

출장·여행에서 중요한 것은 "내일 출발"을 놓치지 않는 것이다.
기존 `notificationTime` 하나를 그대로 쓰므로 필드가 늘지 않고 예약·취소 로직도 그대로다.

### 3-5. 목록: 기간 진행 중이면 매일 "오늘 할 일"에 노출

오늘이 8/23이고 기간이 8/21~8/25면 목록에 뜬다.

> **Discovery 중 발견한 충돌**
> 사용자가 처음에 이 동작을 선택하면서 MVP 경계에서는 "목록 필터·정렬 반영"을 제외했다.
> 그대로 만들면 **출장이 8/25에만 목록에 뜨고 기간 중에는 캘린더에서만 보인다.**
> 지적 후 재확인한 결과 **목록 노출을 이번 범위에 포함**하기로 확정했다.
> 이 항목이 빠지면 기능의 쓸모가 절반이 된다.

## 4. 제약

- **반복 일정과의 조합 제외.** `RecurringTodoService`가 RRULE 인스턴스를 만들 때
  기간까지 복제해야 해서 복잡도가 크게 오른다. UI에서 차단한다
- **Supabase 마이그레이션이 선행 조건이다.**
  ```sql
  ALTER TABLE todos ADD COLUMN IF NOT EXISTS start_date TIMESTAMPTZ;
  ```
  `DTA-3-1`의 `google_event_id`와 달리 **격리가 불가능하다.**
  `start_date`는 생성·수정에서 항상 쓰는 값이라 전용 경로로 뺄 수 없다.
  컬럼이 없으면 할 일 저장이 실패하므로 **마이그레이션 없이는 배포하면 안 된다.**
- 기존 데이터는 `start_date`가 `NULL`이 되어 하루짜리로 동작한다. 별도 백필 불필요

## 5. 우선순위 — 이번 티켓 경계

**포함**
- `startDate` 필드 (엔티티 / Supabase 읽기·쓰기)
- 폼의 범위 선택 UI (`showDateRangePicker` 또는 시작·종료 개별 선택)
- 캘린더 기간 표시 (`_getTodosForDay` 수정)
- Google Calendar 반영 — `buildEvent`의 `end.date`를 **실제 종료일 + 1일**로
- 목록 `today` 필터·그룹핑 반영

**제외**
- 홈 위젯 (`widget_service.dart`)
- 통계 화면
- 반복 일정과의 조합
- 날짜별 체크

## 6. 리스크

| 리스크 | 대응 |
|---|---|
| **`dueDate` 255곳** | `startDate == null`을 기존 동작과 동일하게 만들어 파급을 차단. 새 분기는 `startDate != null`일 때만 |
| **마이그레이션 미실행 시 저장 실패** | 격리가 불가능하므로 문서와 커밋 메시지에 선행 조건임을 명시. 실기기 확인 전 SQL 실행 필수 |
| 시작일 > 종료일 입력 | 폼에서 검증. 저장 전에 막는다 |
| `startDate`만 있고 `dueDate`가 없는 경우 | 범위가 성립하지 않는다. 폼에서 종료일을 필수로 하거나 시작일=종료일로 정규화 |
| **`DTA-3-1`의 `buildEvent` 테스트가 `end.date = start + 1일`을 사양으로 고정** | 범위 지원 시 이 테스트를 갱신해야 한다. 갱신 대상임을 인지하고 진행 |
| Google Calendar 기존 이벤트 | `googleEventId`가 있으면 `update`로 기간이 반영된다. 재동기화만 하면 된다 |

## 7. 검증

**자동**
- `startDate == null`인 기존 할 일이 이전과 동일하게 동작하는지 (회귀 방지 핵심)
- 캘린더 `_getTodosForDay`가 기간 내 모든 날짜를 반환하는지 (경계: 시작일, 종료일, 중간, 하루 전/후)
- `today` 필터가 기간 진행 중인 일정을 포함하는지
- `buildEvent`가 `end.date = 종료일 + 1일`을 만드는지 (월말·연말 경계 포함)
- 시작일 > 종료일 입력이 막히는지

**수동 (자동 불가)**
- 폼에서 범위를 실제로 선택할 수 있는지
- 캘린더에서 기간이 눈으로 보이는지
- Google Calendar에 여러 날짜에 걸쳐 등록되는지

## 선행 조건

`DTA-3-1`의 실기기 확인이 아직 끝나지 않았다.
캘린더 동기화가 실제로 동작하는 것을 확인하지 못한 상태에서 그 위에 범위 기능을 얹으면
문제가 생겼을 때 원인 분리가 어려워진다. **DTA-3-1 실기기 확인을 먼저 마치는 것을 권한다.**

# 정정 (2026-08-21) — 3-5의 "충돌" 은 존재하지 않았다

## 무엇이 틀렸나

Discovery 3-5 에서 **"목록 노출과 MVP 경계가 충돌한다"** 고 보고했다.
근거는 *"기간 중 목록에 띄우려면 today 필터와 그룹핑을 따로 고쳐야 한다"* 였다.

**전제가 틀렸다.** 착수 전 코드를 확인한 결과다.

| 확인 지점 | 실제 |
|---|---|
| `todo_list_screen.dart:297` | `todosProvider` 를 그대로 쓴다. 필터는 all/pending/completed + 카테고리 + 검색뿐 |
| `todo_grouping_utils.dart` | `groupTodosBySeries` 는 반복 시리즈 묶음이다. **날짜 필터가 없다** |

**메인 목록에는 "오늘" 필터가 애초에 없다.** 마감일과 무관하게 모든 할 일이 나온다.
따라서 범위 일정도 이미 목록에 뜬다. 고칠 것이 없다.

## "오늘 할 일" 이 실제로 사는 곳

날짜로 거르는 곳은 세 군데이고, 그중 둘은 **캘린더 기간 표시와 같은 코드 지점**이다.

| 위치 | 현재 | 이번 범위 |
|---|---|---|
| `calendar_providers.dart:63-64` `todosByDateProvider` | `dueDate` 하루로만 키를 만든다 | **포함** — 기간 내 모든 날짜에 매핑 |
| `calendar_screen.dart:121-136` `_getTodosForDay` | 같은 로직이 중복 구현돼 있다 | **포함** |
| `widget_service.dart:574` `_getTodayTodos` | 홈 위젯 전용 | **제외** (Discovery 합의) |

`selectedDateTodosProvider`(`:91`)가 `todosByDateProvider` 를 그대로 쓰므로,
**앞의 둘만 고치면 "오늘을 선택했을 때 진행 중인 범위 일정이 보인다" 가 자동으로 성립한다.**

## 결론

사용자가 처음 고른 MVP 경계 — **"핵심만: 입력·저장·캘린더 표시" + "Google Calendar 반영"** — 이
이미 목록 노출을 포함하고 있었다. 충돌이 아니라 **같은 작업의 다른 이름**이었다.

추가로 물어 확정한 "목록 노출을 이번에 포함" 은 결과적으로 범위를 넓히지 않는다.
따라서 **원래 경계 그대로 진행한다.**

남는 불일치는 하나뿐이며 의도된 것이다:
**홈 위젯은 기간 중 범위 일정을 보여주지 않는다.** 종료일에만 뜬다.
Discovery 에서 위젯을 제외하기로 합의했으므로 이번 범위 밖이며, 별도 티켓 대상이다.
